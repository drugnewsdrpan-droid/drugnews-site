# Encrypted scheduled queue

This public directory may contain only opaque `<32-lowercase-hex>.dnq` AES-256-GCM bundles. Never place a future title, slug, article, image, release manifest, key, staging directory, archive, or QA report here in plaintext.

The private release manifest is accepted only when it carries one `content_id`/`release_key` and locked version/hash, approved Chinese title/slug/body/metadata, an approved English package or an explicit English `HOLD`, four ordered images per published language (purpose, dimensions, bytes, language, path, SHA-256), primary sources, fixed `publish_at` with `+08:00`, all three independent QA scores at 95 or above with P0/P1 at zero, the QA report evidence, Facebook/Dcard/CMoney schedule dates/order/row IDs, and explicit queued/revoked/superseded state.

Limits are 28 jobs, 89 MiB per encrypted bundle, and 512 MiB total. The runner validates every bundle in opaque job-ID order, decrypts one at a time in a private temporary directory, stages only `publish_at <= now`, and fails closed on a missing key, authentication failure affecting the queue, version/hash mismatch, slug conflict, leak audit failure, or build/QA failure. Due bundles remain in the queue until a separately verified canonical migration exists; report the actual used/28 and remaining slots rather than deleting published bundles. A due job whose locked article files already match `content/published` byte-for-byte is marked `legacy_e4`, is not materialized again, and still must pass candidate and public E4 audits. If a historical article has no canonical manifest/handoff, request it from the content owner; do not reconstruct or rewrite it here.

Production and CI never permit `--force`. GitHub Actions secrets must never be printed, committed, uploaded as artifacts, or copied to shared Drive.

After a content LOCK has been mechanically adapted into a complete private website input, run `node scripts/scheduled_queue.mjs check-input --input=/absolute/private/input` before the website handoff. This reads the same `payloadFromInput` → `validatePayload` contract used by packing. It prints a JSON receipt bound to the exact input manifest SHA-256, declared source LOCK reference, locked version, review binding, job identity, and publish time. The declared source LOCK reference retains the original packaging provenance; this command does not perform a new content review.

Keep `content_qa` and `native_contract` separate in the original handoff/index. A missing receipt or `native_contract.verdict=FAIL` means the website input is awaiting contract acceptance, even when content QA and LOCK are valid. A `PASS` receipt permits the next already-authorized publisher step; it is neither queue acceptance nor public delivery. The command never reads keys, encrypts, stages, edits input or queue files, submits GitHub outputs, or deploys. Save stdout in the original private results directory; keep receipts out of this public encrypted queue. Do not demand this complete-input check before the required package dependencies exist.
